# ADR-0001: Фиксируем решения в формате ADR

- Статус: Принято
- Дата: 2026-11-12

## Контекст

Над проектом AI-SLICE работает команда, и за время разработки мы примем много решений: какой будет интерфейс, на чём писать, как подключать нейросеть. Через пару недель обычно уже никто не помнит, почему выбрали именно так. Из-за этого одни и те же вопросы обсуждают по нескольку раз, а новые участники команды не понимают, что можно менять, а что нельзя.

Преподаватель попросил записывать такие решения отдельно, чтобы потом можно было объяснить, почему, например, сделан веб-интерфейс, а не командная строка.

## Решение

Каждое важное решение записываем в отдельный markdown-файл по одному шаблону. Файлы лежат в папке `docs/adr` в репозитории проекта.

Правила:

- Имя файла: номер и короткое название, например `0003-web-interface.md`.
- Разделы в каждом файле: статус, дата, контекст, решение, рассмотренные варианты, последствия.
- Решение описываем коротко, но с причиной: что было нужно, что выбрали и от чего отказались.
- Принятый файл не переписываем. Если решение поменялось, пишем новый файл и в старом меняем статус на "Заменено".

## Рассмотренные варианты

- Хранить решения в общем чате. Быстро, но через неделю их уже не найти.
- Вести один большой документ. Его неудобно читать и трудно понять, какая часть устарела.
- Один файл на одно решение (выбрано). Решения можно искать по номерам, они лежат рядом с кодом и попадают в историю изменений репозитория.

## Последствия

Плюсы:

- Причины решений сохраняются, и на защите проекта можно показать, как мы к ним пришли.
- Новому участнику достаточно прочитать папку, чтобы понять устройство проекта.

Минусы:

- На запись каждого решения уходит время. Для мелких вопросов (название переменной, цвет кнопки) ADR не пишем, только для тех решений, которые сложно менять потом.
