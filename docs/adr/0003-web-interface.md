# ADR-0003: Основной интерфейс - локальный веб-интерфейс (React + FastAPI)

- Статус: Принято
- Дата: 2026-11-12
- Проект: AI-SLICE. Умная нарезка моделей для 3D-печати
- Уточнено: 2026-11-12 (выбраны технологии: React для фронтенда, FastAPI для бэкенда)

## Контекст

Преподаватель описал идеальный сценарий так: пользователь загружает готовую модель, при необходимости пишет короткий комментарий, а на выходе получает проект для печати, G-код, параметры печати и базовый выбор принтера. Если результат не устраивает, пользователь может ещё раз попросить нейросеть исправить его или поправить настройки вручную.

Значит, интерфейсу нужно уметь:

- принять файл и необязательный комментарий;
- показать выбранные параметры и принтер;
- дать кнопку "переделать" с новым комментарием;
- дать править параметры вручную;
- отдать G-код и проект на скачивание.

Пользователь - оператор или инженер на производстве, он не обязан уметь работать в терминале.

Нарезка и анализ модели могут занимать заметное время, а оператор может загрузить несколько моделей подряд. Поэтому серверу нужно выполнять несколько операций одновременно, не блокируя интерфейс.

Полноценный веб-портал (аккаунты, история пользователей, админ-панель) в проекте не планируется.

## Решение

Основной интерфейс - простое веб-приложение, которое запускается на компьютере пользователя и открывается в браузере. Страница одна или две: загрузка и результат с параметрами.

Технологии:

- фронтенд: React;
- бэкенд: FastAPI (Python, см. ADR-0010).

Отдельно делать командную строку как самостоятельный продукт не будем. Вся логика лежит в отдельном модуле, а бэкенд и интерфейс только вызывают её. Поэтому для тестов и автоматических прогонов те же функции можно запускать из консоли без лишней работы.

Интерфейс доступен только с самого компьютера (или из локальной сети компании), в интернет не публикуется. Это связано с требованием ТЗ не передавать данные без контроля (см. ADR-0006).

Схема работы: React-приложение отправляет запросы в FastAPI, а тот вызывает общую логику проекта (те же функции, что и инструменты MCP-сервера, см. ADR-0004). Готовую сборку фронтенда отдаёт сам FastAPI, поэтому пользователю достаточно запустить одну программу.

### Почему FastAPI

- Высокая производительность. Это важно при работе с 3D-моделями и файлами большого размера.
- Асинхронность "из коробки" на всех уровнях. Это нужно, чтобы выполнять несколько операций нарезки одновременно и не блокировать интерфейс на время долгих задач. Тяжёлые расчёты (анализ сетки, запуск OrcaSlicer) выносим в отдельные процессы, чтобы они не мешали обработке запросов.
- Лёгкость. Для задачи "принять файл, вызвать логику, отдать результат" достаточно небольшого API, лишнее не нужно.
- Автоматическая проверка данных и документация API. Структура параметров из ADR-0007 описывается один раз и используется и в проверке, и в документации.

### Почему не Django

Django хорош для полноценных веб-порталов: аккаунты, история, админ-панель, работа с базой данных. В нашем проекте этого нет и не планируется, поэтому большая часть возможностей Django осталась бы неиспользованной, а проект стал бы тяжелее и медленее. Классический Django также менее удобен для асинхронных задач, чем FastAPI.

## Рассмотренные варианты

- Только командная строка. Проще всего написать, но оператору неудобно: нельзя наглядно показать параметры, править их кнопками и сравнивать результат. Сценарий из ответа преподавателя в консоли выглядел бы тяжело.
- Настольное приложение (Tkinter или Qt). Работает без браузера, но дольше собирать, сложнее обновлять и показывать на демо.
- Плагин внутри самого OrcaSlicer. Выглядел бы привычно, но интерфейс OrcaSlicer написан на C++, и это ведёт к форку, от которого мы отказались в ADR-0002.
- Веб-интерфейс на Django. Подходит для порталов с аккаунтами и админ-панелью, которых у нас нет. Отклонено.
- Простые HTML-страницы без фронтенд-фреймворка. Это был первоначальный вариант. Для формы с редактируемыми параметрами, историей изменений и кнопкой "переделать" состояние интерфейса быстро усложняется, и React с этим справляется удобнее.
- React + FastAPI (выбрано). Лёгкий и быстрый бэкенд, удобный интерфейс для редактирования параметров, удобно показывать на защите, работает на любой системе.

## Последствия

Плюсы:

- Всё, что нужно пользователю по ответу преподавателя, помещается на одной-двух страницах.
- Сервер не блокируется на время нарезки, можно обрабатывать несколько задач одновременно.
- Фронтенд и бэкенд разделены чётким API, их можно разрабатывать и проверять независимо.
- Тот же интерфейс можно показать заказчику без установки сложных программ.

Минусы:

- В проекте два стека: Python и JavaScript/TypeScript. Для сборки фронтенда нужен Node.js (подробнее в ADR-0010).
- Нужно написать и поддерживать фронтенд и API между частями. Чтобы не тратить время, интерфейс делаем простым: форма загрузки и таблица параметров, без лишних библиотек.
- Если нужно будет несколько пользователей с учётными записями и историей, придётся добавлять это отдельно. Для MVP это не требуется.
- Просмотр 3D-модели в браузере в первую версию не входит. Если останется время, добавим.
