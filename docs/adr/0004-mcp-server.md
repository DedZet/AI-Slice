# ADR-0004: Возможности системы оформляем как MCP-сервер

- Статус: Принято
- Дата: 2026-11-12
- Уточнено: 2026-11-19

## Контекст

В ТЗ прямо указан MCP-интерфейс: через него агент должен получать доступ к профилям, моделям, проверкам и истории печати, а позже к внешним инструментам, базе профилей, очереди печати и документации. MCP (Model Context Protocol) - это общий способ описать для нейросети набор инструментов, которые она может вызывать.

Нужно решить, как именно агент будет общаться с нашей программой: вызывать функции напрямую в коде или через MCP, и как это будет устроено внутри.

### Принтер

Что делаем:

- Принтер описывается профилем OrcaSlicer (собственным профилем Силикрона). Из профиля берём размер стола, диаметр сопла, ограничения скоростей и температур, начальный и конечный G-код.
- В `profiles/printers/` лежит один файл на принтер. Добавить принтер - значит добавить файл, код не меняется.
- Все пороги анализа (допустимый угол нависания, минимальная толщина стенки, предельная высота) считаются от параметров принтера и материала, а не зашиты в код.

## Решение

### Три слоя

- Вся логика живёт в ядре, обычных Python-функциях без знания о MCP. Их можно вызвать из теста или консоли.
- MCP-сервер - тонкая обёртка: для каждой функции ядра описывает имя, короткое описание и типы входа и выхода (берутся из аннотаций Python и моделей pydantic), и больше ничего не делает.
- FastAPI-бэкенд (ADR-0003) - вторая такая же обёртка над тем же ядром. Так нет двух реализаций одного и того же.

### Как это работает технически

1. Сервер написан на официальной библиотеке MCP для Python (интерфейс FastMCP).
2. Транспорт: `stdio` для запуска дочерним процессом из нашего бэкенда и для подключения внешних клиентов (например, десктопных приложений с поддержкой MCP). Если понадобится удалённый доступ в локальной сети компании, включаем HTTP-транспорт той же библиотеки; код инструментов при этом не меняется.
3. Цикл агента находится в модуле `aislice.agent` и работает так: бэкенд получает запрос -> модуль агента отправляет нейросети (через модуль общения с моделью из ADR-0006) текст задачи и список инструментов -> нейросеть просит вызвать инструмент -> агент вызывает его через MCP-клиент -> результат возвращается нейросети -> так до тех пор, пока нейросеть не вернёт итоговое решение и пояснение. Число шагов ограничено (например, 8), чтобы агент не зациклился.
4. Файлы по сети не гоняем. Инструменты работают с идентификаторами: `model_id` (загруженная модель) и `project_id` (рабочий проект). Всё лежит в папке `workspace/<project_id>/`: исходная модель, `project.json` (ADR-0007), результаты анализа, G-код.
5. Результаты инструментов - короткий JSON с числами (десятки строк, не мегабайты). Это нужно и для качества работы нейросети, и для требования ADR-0006 не отправлять геометрию наружу.
6. Тяжёлые инструменты (`analyze_orientations`, `slice_model`) выполняются в отдельных процессах ядра, чтобы не блокировать сервер (ADR-0003).
7. Ошибки возвращаются как структурированный ответ с понятным текстом ("модель не замкнута, исправлено автоматически / не удалось исправить"), чтобы нейросеть могла объяснить причину пользователю, а не упасть.

### Набор инструментов

| Инструмент | Что делает |
|---|---|
| `inspect_model(model_id)` | Проверяет и при необходимости чинит сетку, возвращает габариты, объём, число полигонов и тел, предупреждения (ADR-0005, блок A)
| `analyze_orientations(model_id, printer_id, material_id)` | Для 6 положений на столе возвращает таблицу чисел: высота, площадь касания, нависания, мосты, объём поддержек, тонкие стенки, устойчивость (ADR-0005, блоки B-E) |
| `list_printers()` | Список принтеров и материалов, доступных в MVP |
| `get_profile(printer_id, material_id)` | Допустимые диапазоны и значения по умолчанию для параметров печати |
| `set_parameters(project_id, changes, comment)` | Проверяет значения по допустимым диапазонам профиля (валидация профиля печати, ТЗ, п. 3) и записывает положение, параметры и пояснения в `project.json` с пометкой "ИИ"; поля, изменённые человеком, не перезаписывает (ADR-0007). Значение вне диапазона отклоняется с понятной причиной | да |
| `slice_model(project_id)` | Поворачивает модель, собирает настройки OrcaSlicer из `project.json`, запускает его и возвращает время, расход материала и путь к G-коду |
| `check_result(project_id)` | Проверяет итог простыми правилами (ADR-0008) и возвращает список рисков |

Чего среди инструментов нет намеренно:

- Нет инструмента "принять результат" и "скачать G-код". Подтверждение делает человек только через интерфейс (ADR-0008), нейросеть к этому доступа не имеет.
- Нет инструмента "прочитать файл" и "запустить команду". Нейросеть не лезет в файлы и в OrcaSlicer напрямую.
- Нет отдельных инструментов для каждого параметра печати: все они записываются одним `set_parameters`.

### Правила описаний инструментов

- Описание - одно-два предложения: что делает и когда вызывать.
- Входные поля имеют короткие названия и допустимые значения (например, список `printer_id` приходит из `list_printers`).
- Каждое описание проверяем на 3-5 тестовых моделях: нейросеть должна вызывать инструменты в правильном порядке (`inspect_model` -> `analyze_orientations` -> `get_profile` (и при желании `get_history`) -> `set_parameters` -> `slice_model` -> `check_result`) без подсказок.

## Рассмотренные варианты

- Вызывать функции напрямую из кода без MCP. Проще на старте, но это не выполняет требование ТЗ, и мы теряем возможность подключить наши инструменты к другим программам-клиентам.
- Придумать свой протокол или обычный REST-интерфейс для нейросети. Это лишняя работа, и нам пришлось бы самим объяснять каждому клиенту, как им пользоваться.
- Отдавать нейросети по одному инструменту на каждую метрику геометрии (нависания, касание, поддержки отдельно). Нейросеть делала бы много лишних вызовов и путалась. Решили: один инструмент возвращает всю таблицу.
- MCP-сервер как тонкая оболочка над ядром (выбрано). Стандартный способ, под него есть готовая библиотека, и заказчик сможет подключать свои сервисы.

## Последствия

Плюсы:

- Выполняется требование ТЗ.
- Каждый инструмент можно проверить отдельно, без нейросети: это обычные функции.
- Веб-интерфейс и нейросеть используют одну и ту же логику.
- Позже можно подключить базу материалов и принтеров Силикрона или очередь печати как ещё один инструмент, с подтверждением человеком (ADR-0008).

Минусы:

- Появляется дополнительный слой, протокол придётся изучить.
- Качество работы зависит от того, насколько ясно описаны инструменты, поэтому описания нужно проверять на тестовых моделях и на выбранной нейросети Alice AI LLM (ADR-0006): разные модели по-разному вызывают инструменты, поэтому описания подгоняем под неё.
- Конкретные принтеры Силикрона неизвестны (ТЗ их не называет), поэтому до ответа заказчика работаем на типовых профилях.
